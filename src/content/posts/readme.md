# 博客文章整理与生成约定

这份文件用于提醒下次整理文章的流程。它是仓库说明，不是博客文章；`src/content.config.ts` 已通过 `!readme.md` 将它排除出 `posts` 集合。不要给本文件添加文章 frontmatter，也不要让它进入文章列表、归档、专题、RSS 或搜索索引。

## 下次可以直接这样交代

> 请先阅读 `src/content/posts/readme.md`，按这里的约定整理 `src/content/posts/具体目录` 下的新文章。发布日期固定为 `YYYY-MM-DD`，补齐元数据、检查正文和图片、关联现有专题与系列、添加对应学习动态，并完成项目检查。需要提交时，我会单独提出。

日期请写完整年份。例如本次 Firefly 评论文章的“9.20”按 `2026-09-20` 处理。以后使用当次指定的日期，不要固定沿用本次日期，也不要因为图片是在其他日期上传就改动文章发布日期。

## 目录与文件

- 按主题保存在 `src/content/posts/<领域>/<技术>/<专题>/`，延续现有目录与中文文件名习惯。
- 原稿已存在时直接整理原文件，保留内容、截图顺序、参考来源和原有技术细节；避免另建重复文章或无必要地重命名。
- `assets/` 用于导入时暂存图片；图片上传并验证后，替换引用，再清理确认不再使用的本地文件。
- `.md` 优先；确实需要组件交互时使用 `.mdx`。

## 文章元数据

每篇文章开头添加 YAML frontmatter。必填字段是 `title` 和 `published`，其余按内容补齐，下面是本次文章的结构示例：

```yaml
---
title: "Firefly 博客接入 Waline 评论系统"
published: 2026-09-20 10:30:00
description: 对比评论方案，记录 Waline 服务端部署、域名绑定和 Firefly 客户端接入流程。
image: "已验证可访问的封面图片 URL"
tags: ["Astro", "Firefly", "Waline", "评论系统", "Vercel", "Neon"]
category: Web 开发
series: "Firefly 博客搭建与实践"
seriesOrder: 1
hubs: ["firefly-features"]
draft: false
lang: zh-CN
---
```

- `title`：清楚说明文章内容，避免直接把整个文件路径作为标题。
- `published`：遵守当次指定的日期；同一批文章需要排序时，可以在该日期内安排合理时刻。日期不要加引号，当前 schema 使用 `z.date()`。
- `updated`：只有实际需要记录更新时间时再填写，不要为了补齐字段强行添加。
- `description`：一两句话说明内容和读者能完成什么，避免直接截断正文。
- `tags`：围绕技术、工具和文章主题选择，保持已有标签的拼写一致。
- `category`：优先复用已有分类，如 `Web 开发`、`编程语言`、`Python 学习`、`运维与系统管理`。
- `series` / `seriesOrder`：同一组连续文章使用一致的系列名称，按学习顺序排列，新增前检查是否已有同名系列和序号。
- `hubs`：填写 `src/content/hubs/` 中现有专题文件的 ID，不带 `.md`。Firefly 文章可使用 `firefly-features`；只在现有专题不适用时新建专题。
- `image`：有合适封面时使用图床 URL，没有就省略。不要填写不存在的图片路径，也不要为了补封面强行使用随机图。
- `draft: false` 表示正式发布；`lang: zh-CN` 用于中文文章。

当前文章链接根据 Astro 内容集合的 `entry.id` 生成。默认 glob loader 会优先使用 frontmatter 中的 `slug`；没有 `slug` 时根据目录和文件名生成 ID。现有整理文章通常不额外设置 `slug`，而 `scripts/new-post.js` 会生成包含拼音的 `slug`。注意检查这两种方式生成的链接，已经发布的文章不要随意修改路径或 `slug`；最终地址以构建结果为准。

## 正文整理

1. 保留原稿的表达习惯和主要内容，修正明显错字、前后矛盾、过时步骤及无法执行的命令，不随意编造操作结果。
2. 延续已有章节形式：一级章节常用 `# 【一】标题`，子章节常用 `## 【1】标题`；编号连续，补充材料可单独标为 `【补充】`。
3. 列表序号后留空格，截图缩进到对应步骤中，代码块写明语言，如 `bash`、`typescript`、`sql`、`text`。
4. 配置示例与本仓库的实际字段、类型和使用方式保持一致；仅需要配置即可启用的功能，不额外要求读者手写初始化代码。
5. 引用官方文档和原有参考来源；涉及部署、登录、数据库等易变步骤时对照官方说明，区分必需步骤与可选步骤。
6. 不把密钥、数据库密码等凭据放进正文、配置示例或截图；个人服务域名可以作为公开示例。
7. 有长教程时补充故障排查和验证方法，让读者能确认步骤是否成功。

## 图片处理习惯

目前使用 PicList 上传到现有阿里云 OSS 图床，公开地址为 `https://oss.silentdream.top/`。先确认 PicList 正在运行且选中的图床配置正确，沿用已配置的上传规则，不在仓库保存图床凭据。

本机 PicList 上传接口支持 `POST http://127.0.0.1:36677/upload`，JSON 请求体为 `{"list":["图片的绝对路径"]}`；接口地址和鉴权要求以当前 PicList 配置为准。

处理时依次完成：

1. 找出目标文章的本地图片引用，包括正文和 frontmatter 封面，并确认文件存在。
2. 上传图片，记录本地路径与返回 URL 的对应关系。
3. 验证返回 URL 可访问，确认上传数量、图片类型与对应关系正确。
4. 用返回的 URL 替换引用，为截图添加能说明内容的替代文字；封面与正文避免无意义地重复展示。
5. 检查目标目录内是否还有其他文章引用这些本地图片，再删除已上传且不再引用的图片。上传失败或无法验证时保留原图，说明未完成的事项。

文章发布日期与图片上传路径中的日期相互独立，无需为了匹配发布日期修改图床 URL。

## 配套学习动态

沿用已有整理习惯，为完成的文章在 `src/content/dynamic/` 添加对应的一条简短动态：

```markdown
---
published: 2026-09-20 10:30:00
---

给 Firefly 博客接上了 Waline 评论，整理了 Vercel + Neon 部署、域名绑定和客户端配置的流程。文章终于有地方交流了。💬
```

文件名使用 `YYYY-MM-DD-HHmmss.md`，日期与文章一致。内容用自然的一两句话记录本次整理或学习的要点，避免凭空编造经历；新增前检查有没有重复动态。

## 新建文章命令

从零创建文章时，在项目根目录执行：

```bash
pnpm new-post "platform/astro/firefly/新文章标题"
```

脚本会创建目录和基础 frontmatter，默认发布日期是执行当天。执行后仍需按当次要求调整日期、标题、摘要、标签、系列和专题。已经有原稿时不用再次运行，以免重复创建。

## 验证与收尾

文章、图片或渲染相关修改完成后，在项目根目录执行：

```bash
pnpm check
pnpm type-check
pnpm build
```

使用 `pnpm dev` 或 `pnpm preview` 检查文章日期、封面、目录、代码块、步骤与截图，并确认系列和专题收录正确、README 没有进入公开文章或搜索索引。

检查构建更新的 `src/constants/lqips.json`、`src/constants/github-card-data.json` 等生成数据，只保留与本次任务有关的变化，保留已有未提交修改。验证优先使用现有检查或临时命令，不保留新建测试文件、测试目录或临时脚本。

完成后说明处理了哪些文章、采用的发布日期、图片处理结果以及验证情况。Git 提交按用户当次要求执行；提交前完整阅读项目的 `skills/git-commit/SKILL.md`，只提交授权范围。
