# 【一】镜像与容器

前面说 Docker 能把应用交付为镜像，再从镜像运行容器。这里把两个概念放到一起看：

- **镜像（image）**：只读的文件系统层和元数据，例如默认启动命令、环境变量等。它是创建容器的模板，不是一个已经运行的进程。
- **容器（container）**：由镜像创建的运行实例，包含进程、隔离配置和自己的可写层。同一个镜像可以创建多个容器，互不共用各自的可写层。

![同一镜像创建多个容器](https://oss.silentdream.top/2026/09/29/17-59-31-e470cfb2-3626a8528413b5ae141ed58f9afacbe4-2e7878.png)

图中的 MySQL 5.7 是旧版示意，不代表现在应选用该版本；新项目应查看镜像维护状态和数据库官方支持周期。

容器并非先完整复制一份镜像文件再运行；通常会复用镜像的只读层，在上面叠加容器可写层。因此删除容器后，可写层中的数据通常会消失。需要保留数据库或用户文件时，应使用卷或绑定挂载。

# 【二】镜像仓库与 Docker Hub

镜像可以保存在**注册中心（registry）**中；其中按名称组织的镜像集合通常称为**仓库（repository）**。例如 Docker Hub 是常见的公共注册中心，团队也可以使用私有注册中心。`docker pull` 下载镜像，`docker push` 上传镜像。

镜像引用通常包括仓库名和标签，例如 `nginx:alpine`。标签便于阅读，但可能被更新；正式部署需要可重复性时，应固定具体版本或镜像摘要。下载别人发布的镜像前，要确认发布者、更新情况和可信度。

# 【三】Docker 是怎样接收命令的

Docker 使用客户端与服务端的方式工作：

1. 在终端运行 `docker run ...`，**Docker CLI** 发出请求。
2. **Docker Engine** 接收请求，管理镜像、容器、网络和卷。
3. Engine 在需要时从镜像仓库拉取镜像，随后创建并启动容器。

![CLI、Engine 与镜像仓库的关系](https://oss.silentdream.top/2026/09/29/17-59-32-e082ea28-439e0bb06163d135d06722af9e28c4a7-d23141.png)

CLI 可以连接本机，也可以连接配置好的远程 Engine。日后发现“本机明明有镜像却找不到”，先检查 `docker context show`，确认命令发给了哪台 Engine。远程 Engine 的访问权限需要妥善保护。

# 【四】一条命令串起这些概念

```bash
docker run --rm -p 127.0.0.1:8080:80 nginx:alpine
```

这条命令让 Docker 查找或拉取 `nginx:alpine` 镜像，创建并启动一个容器，把宿主机本地 8080 端口映射到容器 80 端口。按 `Ctrl+C` 停止后，`--rm` 会删除容器，但不会删除本地镜像。前台运行时终端会持续显示日志。

需要区分的是：**镜像是交付物，容器是运行实例，仓库负责分发，Engine 负责管理，CLI 负责发送命令。**

# 【五】补充：运行时与构建器

- **dockerd**：Docker Engine 中的守护进程，接收 CLI 请求，管理镜像、容器、网络和卷。
- **containerd 与 OCI 运行时**：负责容器运行相关的底层管理与进程创建；初学阶段通常不用绕过 Docker 直接操作它们。
- **BuildKit**：现代镜像构建器，提供缓存、多阶段构建和构建秘密挂载等能力。
- 容器主进程退出，容器就停止；要让应用在前台运行，不要把主进程转到后台后靠无意义的 `tail` 掩盖退出。

练习：执行 `docker version`、`docker info`、`docker context show`，记录服务端版本、资源和连接目标。Docker Desktop 虚拟机的可用资源不一定等于整台电脑的资源。
