Docker 提供隔离和打包能力，但不替代系统更新、应用鉴权、备份与权限管理。开发时为了方便加的参数，放到服务器上可能产生意想不到的暴露。

# 【一】权限最小化

- 优先使用可信、持续维护的基础镜像，定期重建；镜像扫描结果要结合实际可利用性处理。
- 能以普通用户运行的应用，就在 Dockerfile 中使用 `USER`。必要时在运行参数里限制 Linux capabilities、只读根文件系统等，但先验证应用写入目录是否仍可用。
- 不要随意使用 `--privileged`、`--network host`、挂载 `/var/run/docker.sock`。能控制 Docker socket 的进程通常可以控制宿主机；把它交给普通业务容器，风险很高。
- `docker` 组成员在安全意义上接近宿主机 root。远程 Docker API 不应无认证暴露在公网。

# 【二】端口、凭据与镜像

服务只供本机反向代理使用时，发布到 `127.0.0.1`；需要对外开放时，同时检查防火墙、TLS、应用鉴权。不要在 Dockerfile、镜像层或 Git 仓库里放密码、令牌、私钥。部署凭据可通过受控环境变量、密钥文件或专门的密钥系统注入；具体选择取决于部署平台，敏感值仍要防止出现在日志、`docker inspect`、`docker compose config` 等输出中。

推送镜像到仓库前，检查镜像名、标签、目标仓库和是否包含敏感文件。生产部署建议记录实际镜像摘要：

```bash
docker image inspect my-app:1.0 --format '{{json .RepoDigests}}'
```

发布流程可以简化成：构建镜像 → 运行项目检查/扫描 → 推送仓库 → 在测试环境启动并验证 → 固定版本部署 → 观察日志和指标。回滚要提前准备旧镜像和数据库兼容方案。**数据库 schema 变更不能只靠回退镜像解决。**

# 【三】更新时别忘了数据

容器是可替换的，数据卷不能随意替换。更新前做数据库一致性备份，确认新旧版本的数据格式兼容，记录恢复命令。在单机 Compose 上，`docker compose pull`、`docker compose up -d` 可更新服务；它们不会自动验证业务功能，也不保证零停机。

# 【四】一份上线前的实用检查

确认镜像版本明确、服务仅开放必要端口、数据有备份和恢复演练、配置和密钥未进入镜像/仓库、资源和日志不会无限增长、应用有基本健康检查与监控。检查的目的是让下一次故障能恢复，而不只是当天启动成功。

# 【五】补充：构建一次，逐级发布同一镜像

## 【1】案例：推送自己的镜像

前提：已经构建 `my-site:1.0`，并创建有推送权限的 Docker Hub 仓库。将 `你的账号` 替换为真实账号，不要直接照抄占位符。

```bash
docker login
docker tag my-site:1.0 你的账号/my-site:1.0
docker push 你的账号/my-site:1.0
```

登录按 CLI 指引完成，不把访问令牌写到命令参数或文档中。推送成功后记录仓库返回的 digest，或重新拉取仓库镜像后查询 `RepoDigests`。**只有本地构建、尚未推送的镜像，RepoDigests 可能为空**，不能把本地 IMAGE ID 当成仓库摘要。

## 【2】测试环境和生产环境使用同一产物

- CI 从确定的代码提交构建，完成项目检查、依赖与镜像扫描，再推送注册中心。
- 记录推送后的不可变摘要；测试、生产和回滚使用已验证的摘要，不分别重新构建“同一个标签”。
- 发布后观察健康接口、日志和关键业务指标。单机 Compose 的更新可能重新创建容器，不自动提供零停机或跨主机容错。
- 回滚镜像前检查数据库迁移与配置是否仍兼容；镜像回退与数据恢复是两件事。

## 【3】最小权限示例

```yaml
services:
  web:
    image: my-app:1.0
    read_only: true
    tmpfs:
      - /tmp:size=16m
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
```

这是配置片段，要求 `my-app:1.0` 已存在且应用兼容这些限制。只读根文件系统不影响单独声明的可写卷；需要写入文件的位置应逐项确认，不能套完参数就认为验证通过。

## 【4】上线与恢复小结

- 卷保证容器重建后仍可读取数据，备份则处理误删、损坏和迁移；数据库优先原生一致性备份。
- 至少在隔离环境恢复一次备份，检查内容、业务可读性和所需时间。
- 若开始需要多节点调度、自动故障迁移和大规模滚动发布，再学习 Swarm、Kubernetes 或托管平台；单机 Compose 仍可用于边界清楚的小服务。
