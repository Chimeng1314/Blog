# 【一】练习目标与服务关系

- 本篇把镜像构建、容器互联、数据卷和健康检查串起来。
- 需求：访问 Flask 页面时，Redis 中的计数加一；删除并重建容器后，计数仍保留；Redis 暂时停止时，Web 返回明确的 503，而不是卡住。
- 本篇参考 [OliverChiu 的 Docker 学习笔记](https://www.oliverchiu.com/kb/essay/docker-study)中的 Flask + Redis 实践思路，按本套笔记的命名和步骤重新组织。以下是学习示例，不是完整生产部署。

## 【1】准备文件

在新的 `docker-counter-lab` 目录中准备以下五个文件。Linux/macOS/WSL 可用 `mkdir -p docker-counter-lab && cd docker-counter-lab`；Windows PowerShell 也可通过资源管理器建目录并用编辑器保存文件。

```text
docker-counter-lab/
├── app.py
├── requirements.txt
├── Dockerfile
├── .dockerignore
└── compose.yaml
```

# 【二】编写应用与镜像

## 【1】app.py

```python
import os

from flask import Flask, jsonify
from redis import Redis
from redis.exceptions import RedisError

app = Flask(__name__)
store = Redis(
    host=os.environ.get("REDIS_HOST", "redis"),
    port=int(os.environ.get("REDIS_PORT", "6379")),
    socket_connect_timeout=2,
    socket_timeout=2,
)


@app.get("/")
def index():
    try:
        visits = store.incr("visits")
        return jsonify(message="Hello, Docker!", visits=visits)
    except RedisError:
        return jsonify(error="Redis 暂时不可用"), 503


@app.get("/health")
def health():
    try:
        store.ping()
        return jsonify(status="ok")
    except RedisError:
        return jsonify(status="unavailable"), 503
```

- `REDIS_HOST=redis` 使用 Compose 服务名；写成 `localhost` 就会访问 Web 容器自己。
- `/health` 不增加计数；探测 Redis 是因为它是本例的关键依赖。
- 每次访问都可重新尝试连接，设置超时并返回 503；真实业务还应按操作的幂等性设计有限重试，不能盲目重试写操作。

## 【2】requirements.txt

```text
Flask>=3.1,<4
redis>=6,<8
gunicorn>=23,<24
```

这是学习用兼容范围，不是锁文件；重复构建时可能解析到不同版本。正式项目应生成精确依赖锁和哈希，并在升级后验证。

## 【3】Dockerfile

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN python -m pip install --no-cache-dir -r requirements.txt
RUN groupadd --gid 10001 appuser \
    && useradd --uid 10001 --gid appuser --no-create-home appuser
COPY --chown=appuser:appuser app.py .
USER appuser
EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "--access-logfile", "-", "--error-logfile", "-", "app:app"]
```

- 先装依赖再复制代码，便于缓存复用。
- 使用 Gunicorn 启动应用，不把 Flask 开发服务器当成正式服务方式。
- 以非 root 用户运行；日志写标准输出/错误；监听 `0.0.0.0:8000` 才能接收容器外请求。

# 【三】使用 Compose 编排

## 【1】compose.yaml

```yaml
name: docker-counter-lab
services:
  web:
    build: .
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      REDIS_HOST: redis
      REDIS_PORT: "6379"
    depends_on:
      redis:
        condition: service_healthy
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3)"
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped
    read_only: true
    tmpfs:
      - /tmp:size=16m
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL

  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

volumes:
  redis-data:
```

- Compose 默认创建项目网络，两项服务按名称互联；Redis 没有发布端口。
- AOF 将 Redis 写操作持久化到 `/data`，卷独立于容器。默认同步策略仍可能在故障时丢失最近一小段写入，不能视作无损保证或备份。
- Web 根文件系统只读，需要写入的 `/tmp` 单独用 tmpfs 提供。限制应与应用行为一起验证。

## 【2】构建与验证

在项目目录中执行：

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail 50 web
curl http://127.0.0.1:8000/
curl http://127.0.0.1:8000/health
docker compose exec web id
docker compose exec redis redis-cli GET visits
```

Windows PowerShell 把 `curl` 改为 `curl.exe`。也可用浏览器多次访问 `http://localhost:8000/`；预期 JSON 的 `visits` 逐次增加，健康接口返回 `status: ok`，`id` 显示 UID 10001。首次启动等待健康状态变化，不要立即把 `starting` 判为失败。

## 【3】验证持久化

```bash
docker compose down
docker compose up -d
docker compose exec redis redis-cli GET visits
```

重建后计数应仍在；再次访问首页会继续增加。`down` 默认保留命名卷，不需要每次都指定网络名或容器 IP。

# 【四】故障实验与更新

## 【1】停止依赖

```bash
docker compose stop redis
curl -i http://127.0.0.1:8000/
docker compose ps
docker compose start redis
```

停止 Redis 后预期 Web 返回 503，健康检查经过若干次失败后变成 `unhealthy`。恢复后再次访问 `/health` 应成功。`depends_on` 主要控制启动阶段，不负责运行期间自动恢复依赖，也不保证 unhealthy 容器会自动重启。

## 【2】更新应用

修改 `app.py` 的响应文字后：

```bash
docker compose up -d --build web
docker compose logs --tail 50 web
```

确认新文字生效，再观察健康状态。这里没有把源码绑定挂载进容器，所以只改宿主文件不会自动更新运行中的代码。

## 【3】清理与验收

```bash
docker compose down
```

这条保留计数。**仅当确实要清空练习数据时**才执行 `docker compose down --volumes`；先核对当前目录、项目名和卷归属。

- 能解释宿主机 8000、Web 容器 8000 和 Redis 容器 6379 的区别。
- 能证明删除服务容器后计数仍存在，并说明删除卷的影响。
- 能用状态、日志和健康接口定位 Redis 停止，不使用全局清理命令。
- 生产部署还需要固定镜像摘要、精确依赖锁、Redis 鉴权、备份恢复、资源限制、TLS、监控与回滚，见[安全与发布](/posts/om/docker/110安全与发布/)。
