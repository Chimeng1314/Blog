当应用需要 Web 服务、数据库和缓存时，连续敲很多条 `docker run` 容易漏参数。Compose 用 `compose.yaml` 记录服务、网络、卷和配置，然后用一条命令启动。现在优先使用 **`docker compose`（空格）**。

![Compose 中的服务、网络与卷](https://oss.silentdream.top/2026/09/29/17-59-28-24e3beb3-07-Compose%E7%BB%93%E6%9E%84-f635a8.svg)

# 【一】一个可以读懂的例子

```yaml
services:
  web:
    build: .
    ports:
      - "127.0.0.1:8080:8000"
    environment:
      DATABASE_URL: postgres://app:example@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: example
      POSTGRES_DB: app
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  db-data:
```

这段示例假设当前目录有能监听 8000 端口的 Dockerfile/应用，不能脱离应用文件直接启动。`example` 只是教学密码。`web` 通过服务名 `db` 访问数据库的容器端口 5432；数据库没有 `ports`，因此不向宿主机发布端口。`depends_on` 配合健康检查可以等待数据库“报告健康”，但应用仍应实现重试，因为数据库以后还可能重启。

# 【二】常用命令

```bash
docker compose config        # 展开并检查配置
docker compose up -d         # 后台创建/启动
docker compose ps
docker compose logs -f web
docker compose exec web sh   # 镜像有 sh 时适用
docker compose restart web
docker compose down          # 停止并删除项目容器/网络，默认保留命名卷
```

修改 Dockerfile 后用 `docker compose up -d --build` 重建并应用；只改 Compose 配置时，`up -d` 会按需要重建容器。`docker compose down -v` 会连项目卷一起移除，数据库数据可能因此消失。

# 【三】环境变量与 `.env`

Compose 会读取项目的 `.env` 供 `${VAR}` 插值，容器内是否有某个变量，仍由服务中的 `environment`、`env_file` 等定义决定。`${VAR}` 未设置时可能被替换为空；关键配置可用 `${VAR:?请设置 VAR}` 强制检查。不要把包含真实密码的 `.env` 提交到 Git，也不要误以为它是加密存储。

例如：

```yaml
services:
  web:
    image: my-web:${APP_VERSION:?请设置 APP_VERSION}
    environment:
      APP_MODE: production
```

`docker compose config` 会展开变量，**可能在终端显示敏感值**。生产环境需要限制谁能读取 Compose 文件、环境变量和 Docker 管理接口，并采用合适的密钥方案。

# 【四】补充：项目名与命令边界

## 【1】项目名决定资源归属

- 默认项目名通常来自项目目录；可用顶层 `name:` 或 `docker compose -p 项目名` 指定。
- 自定义项目名后，后续所有命令应使用同样的项目名、配置文件和目录，避免误以为容器或卷丢了。
- 多个副本用不同项目名可以分离容器、网络和卷，但宿主机端口仍不能冲突。

## 【2】exec、run、restart 与 up

| 命令 | 作用 | 适用条件 |
| --- | --- | --- |
| exec | 在已有服务容器中运行命令 | 容器需运行且具备对应工具 |
| run --rm | 按服务配置创建一次性容器 | 默认不发布服务端口，适合管理任务 |
| restart | 重启已有容器 | 不应用修改后的环境变量等配置 |
| up -d | 按最终配置创建/更新服务 | 配置变更应使用它 |
| stop | 停止并保留容器 | 之后可以 start |
| down | 删除项目容器和网络 | 默认保留命名卷；external 资源不由它删除 |

## 【3】多个配置文件

```bash
docker compose -f compose.yaml -f compose.dev.yaml config
docker compose -f compose.yaml -f compose.dev.yaml up -d
```

上面要求两个文件确实存在，后一个会按 Compose 合并规则补充或覆盖前一个；不能把它简单理解成所有字段都完全替换。相对路径通常以第一份配置文件为基准。先检查 `config` 的最终结果；输出可能含凭据。

`profiles` 可让调试服务按需启用，例如为工具服务加 `profiles: [debug]`，再用 `docker compose --profile debug up -d`。完整练习见[【13.1】Flask 与 Redis](/posts/om/docker/131flask与redis综合练习/)。
